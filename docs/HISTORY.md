# Firn — history of what landed and why

Moved out of CLAUDE.md's "Where we are" so that file stays short, word for word. Entries are roughly newest first, as they were written. User-facing release notes are in `CHANGELOG.md`; this is the developer-facing "what, where in the code, why, and how it was checked".

**Adding to this file:** when a step lands, add its detailed entry here (what changed, where in the code, how to check it). In CLAUDE.md, keep only the few lines under "Where we are".

## Phase 6 (polish & shipping) log

Phases 1–5 were done before this log began: Firn browses, has the sidebar with vertical tabs, pins, Basecamp, spaces, session restore, Lookout, split view, and the command bar.

- **Phase 6 (polish & shipping): in progress.**
  - Done: find in page, zoom, right-click menus, downloads, PDF viewer, site permissions, history, settings (including the address bar's two looks), saved passwords, scam and malware warnings (Google Safe Browsing), the welcome, Fraunces brand headings, the Firn menu at the bottom-left, the Windows installer ("Firn Setup.exe"), version 0.1.0, the MPL 2.0 license, and automatic Windows and Mac builds on GitHub (releases attach the downloads), and the first round of testing on real Macs (traffic lights that move with the sidebar, page corners matching macOS 26+, the window's top edge to grab it).
  - **The empty space under the tabs moves the window** (Firn's first outside contribution, by whzmsa: dwurgy/firn#70): a `.space-pane` behind the tab list carries `-webkit-app-region: drag` in the main window, and the list, the space's name, and the tabs stay `no-drag` (`src/ui/Sidebar.tsx`, the drag rules in `src/ui/styles.css`). Follow-up: on Windows, a right-click on a drag area never reaches the page (Windows shows its window menu: Restore, Move, Size…), which would have taken away the sidebar's right-click menu exactly where people reach for it. Now the main window's `system-context-menu` (`src/main.ts`, beside `showSidebarMenu`) shows the sidebar's menu instead when the mouse is in the docked sidebar (below the bar with the address bar at the top); the top bar keeps Windows' menu, as a title bar does. Also: the PR's two files formatted (lint failed on main). Checked: the `appregion` check (the pane drags, its contents don't; a pretended Windows right-click under the tabs shows the sidebar's menu, one on the top bar doesn't). To be checked on David's Windows PC: dragging the window from under the tabs; right-clicking there shows Change color… (not Restore, Move, Size…); right-clicking the top bar still shows Windows' menu.
  - **Google sign-in: Firn introduces itself as Firefox there** (two testers, Amsterford and dhyankrishna24 in dwurgy/firn#72, got "This browser or app may not be secure" even after 0.9.2's short Chrome version; Google can still tell Firn is built on Electron): requests to `https://accounts.google.com/*`, and only those, are sent Firefox's name for the system (its version is Chrome's main version + 3, so it stays current as Electron updates) and none of Chromium's "which browser" hints (`Sec-CH-UA…`), as Min does. David's call: it gets around a check Google put there on purpose, and Google may tighten it again. Where: `setUserAgentFor` in `src/engine/electron.ts` (the session's one `onBeforeSendHeaders` hook), set up with `firefoxUserAgent()` in `src/main.ts`. Not changed: what the page's own scripts read (`navigator.userAgent` still says Chrome, as in Min), and Firn's own fetch for the tab's icon. Checked: the `useragent` check (a pretend sign-in address on port 8768, `FIRN_GOOGLE_SIGN_IN_TEST`: the page and what it loads get Firefox's name and no hints; other sites still see Chrome, with hints). To be checked: a fresh Google sign-in in Firn on Windows, in a tab and through a "Sign in with Google" popup.
  - **Security audit F13 fixed: showing a saved password asks if it's you.** Settings > Saved passwords showed or copied any password on a click, so anyone at an unlocked computer could read them all. Now Show and Copy first ask the computer's own check (`OwnerGate` in `src/osauth.ts`): Touch ID on a Mac (`systemPreferences.promptTouchID`), Windows Hello (PIN, fingerprint, or face) on Windows, through the PowerShell that comes with Windows (`UserConsentVerifier`; full path to powershell.exe, two fixed scripts, nothing from outside goes in). One yes holds for a minute or until the sheet closes, whichever comes first; a yes given after the sheet closed unlocks nothing. The check lives in the main process (`revealChecked` in `src/main.ts`: `passwords:reveal` and `passwords:copy` only answer while the sheet is open). Where the computer has no such check (a Mac without Touch ID or with its lid closed, Windows without Hello, Linux), David's call, option (a), unlike Chrome (which falls back to the computer's password): Show and Copy aren't there, and a quiet line says why ("set up Windows Hello…"); passwords still fill in on their sites. Nothing is sent or stored. Checked: the `passwords` check (answers come from a test-only hook, `FIRN_INSECURE_TEST_PASSWORDS`: no check available, cancelled, yes, a yes holding for Copy, and the sheet closing locks it again; the bridge refuses while the sheet is closed). To be checked on David's Windows PC: Show asks for Windows Hello (and the Hello prompt comes up in front of Firn, not behind it), cancelling shows nothing, and Copy right after doesn't ask again; on the Mac, Touch ID.
  - **Security audit F7 fixed: permissions belong to the tab's site.** When a page embeds another site in a frame (an ad, a video-call widget) and that frame asked for the camera, location, and so on, the question named the frame's site and the answer was saved for it, so the question didn't match the address bar, and the site menu never listed the answer. Now (`topOrigin` in `src/engine/electron.ts`, used by both the permission request and check handlers) the question names, and the answer is saved for, the site actually loaded in the tab (its top frame's committed origin), as Chrome does; a frame only gets that far if the page allowed it (`<iframe allow="camera">`, enforced by Chromium). Notifications from another site's frame are refused outright (Chrome does too; mostly ads). A site's background worker (no page) still uses its own site. Check: `perm` (a `localhost` frame inside a `127.0.0.1` page, `tests/e2e/site/perm-frame.html`).
  - **Security audit F8 fixed: no Windows tools from web pages.** A page can ask to open a link in another app (zoommtg:, msteams:, mailto:), and Firn asks first. But some kinds of link start Windows tools that attackers have used straight from web pages: ms-msdt ("Follina", ran code), search-ms (shows a remote folder as if it were on this PC, to trick people into opening a file), ms-officecmd and ms-appinstaller (ran or installed programs). One wrong "Allow" was enough. Now those, plus the old scripting and help-file kinds Chrome itself refuses (vbscript, hcp, ms-its, shell, …), are refused without a question, even if someone allowed them before (`REFUSED_SCHEMES` in `src/engine/electron.ts`, checked in the permission request handler before Firn's prompt). A link with no readable kind is refused too. Everything else still asks, as before. Check: `perm` (ms-msdt: and search-ms: links bring no prompt; a made-up app's link still asks).
  - **Security audit F11 fixed: no addresses in the diagnostics printout.** Ctrl+Shift+D (a hidden helper that prints what each layer of the window is doing, for tracking down a stuck window) named each page by the first 60 characters of its address, breaking the rule that logs never say which sites someone visited. Now a page shows only as its number (`page #12`, from `printDiagnostics` in `src/main.ts`), still enough to tell layers apart. Check: `diagnostics` opens a page with a recognizable address, presses the shortcut, and reads Firn's terminal output (it failed on the old code).
  - **Security audit F12 fixed: the build only uses what it expects.** The build's GitHub Actions were pinned to major tags (`@v5`), which their owners can move, and the build downloaded Microsoft's signing add-on and Apple's Developer ID certificate without checking them. Now every Action is pinned to its full commit (the version in a comment beside it), the signing add-on must match NuGet's own SHA-512 for version 1.0.128 (from its catalog), and Apple's certificate must name the Developer ID G2 authority and be signed by Apple's root, taken from the Mac's built-in roots (no hash: apple.com wasn't reachable from the session, and this check also survives Apple reissuing the file). All in `.github/workflows/build.yml`. Updating an Action or the add-on now means updating its commit or hash too. Check: the next signed build on main passes both new steps; the certificate check was tried locally with a stand-in chain (signed copy accepted, self-made copy refused).
  - **Security audit F10 fixed: a Content Security Policy for Firn's UI.** Firn's own interface (the sidebar, the floating layer, the top bar, the peek) had no policy, so if a page's title, address, or anything else ever slipped into it as HTML, a script in it could run with the UI's bridge to Firn. Now every file served at `firn://app` carries one (`UI_CSP` in `serveUi`, `src/main.ts`): scripts, styles, and fonts only from Firn itself (no inline scripts, no eval, no injected `<style>`), images also from sites (tab favicons are the pages' own addresses) and data: (icons, the paper grain), nothing else (no frames, plugins, forms, or `<base>`). It's a header, not a `<meta>` in index.html, because Vite's dev server (`npm start` and the checks) needs inline scripts; so it applies to real builds only. Check: `csp` packages Firn (about 20 s, keeping the dev build the other checks use), runs the packaged code with plain Electron (the real binary's fuses refuse the debugger), and checks the header, that the sidebar, a favicon, the font, the command bar, and Settings work with nothing refused, and that an injected script doesn't run.
  - **Security audit F9 fixed: downloads.** A page could pour files into Downloads without a click (one script starting download after download), and file names were only cleaned of the characters Windows forbids. Now, as in Chrome, a page may start one download on its own: the first after it opens, after Firn loads an address into it, or after each real press or key in it; more before the next press are quietly refused and leave nothing in the list (`mayDownload` and `downloadUsed` in `src/engine/electron.ts`, reset in `guardWindowOpens`' press listener, `ElectronPage.load`, and "Save image"; decided once per download even with several windows listening). Firn's own downloads ("Try again") come from no page and always go ahead. Names (`cleanName` in `src/downloads.ts`): direction marks (right-to-left override and friends, which make "photo, a right-to-left mark, gpj.exe" show as "photoexe.jpg") are taken out (Chromium already swaps them for "_"; this is a second layer), runs of spaces become one so spaces can't push the real ending out of sight, the dots and spaces Windows drops from the end go, and names longer than 150 characters are shortened, keeping their ending. Not asked about, unlike Chrome's "download multiple files" question: a site that really sends several files from one click gets only the first (say so if that bites). Check: `downloadguard`.
  - **Security audit F6 fixed: only main and releases are signed.** The build (`.github/workflows/build.yml`) ran every push, on any branch, in the `windows-signing` environment that Azure trusts, and handed the Mac signing secrets (repository-wide) to it too, so code pushed to any branch could sign with David's certificates. Now the build job runs in `windows-signing` only for a release or a push to main (`FIRN_SIGN`); any other branch runs in a plain `branch-builds` environment, skips both signing setups, and gets no Apple key, building an unsigned Firn (a basic signature on Mac, so a Mac asks before opening a branch build). Releases still refuse to build unsigned. The other half is a GitHub setting David makes: Settings > Environments > windows-signing > Deployment branches and tags: "Selected branches and tags", with `main` and the tag pattern `v*`; and, optionally, moving the six Mac secrets from the repository into that environment (the workflow reads them the same way). Check: the next branch push's run shows "branch-builds" and no signing steps; the next push to main still signs both.
  - **Security audit F5 fixed: no devices for sites.** Sites can ask for a Bluetooth, USB, serial, or HID device (the Web Bluetooth, WebUSB, Web Serial, and WebHID features, used by things like Arduino tools and some keyboards' setup pages). Firn shows no picker for them, and Electron's Bluetooth default (once any handler is added) picks the first device it finds without asking. Now `src/main.ts` refuses them all, app-wide: every session (`session-created`) cancels the HID, USB, and serial pickers, allows no device (`setDevicePermissionHandler`), and declines Bluetooth pairing (Windows and Linux); every page (`web-contents-created`) cancels the Bluetooth picker. Plain "no" rather than a question: hardly anyone needs it in a calm everyday browser; if testers do, a short "This site wants to connect to a device" question is the answer. Check: `devices` (each handler is in place and refuses a made-up device on offer; a real page asking after a click gets nothing).
  - **Security audit F4 fixed: no client certificates for sites.** A site can ask the browser for a client certificate (a certificate installed on the computer that proves who you are, used by some company and government sign-ins). Electron with no handler quietly sent the first one to any site that asked, which can identify the person. Now an app-wide `select-client-certificate` handler in `src/main.ts` answers with none, so sites that need one show their own error. If testers ever need one, the plain answer is a short "This site asks for a certificate from your computer" question, not a silent default. Check: `clientcert` (a real https site asking, with a test certificate in Chromium's Linux store; a control without Firn's handler shows it would be sent).
  - **Security audit F3 fixed: popup windows show their real site.** Sign-in style popups open as their own windows with no address bar, so a page could call itself anything (a title of "accounts.google.com" on any site). Now `showPopupSite` (`src/engine/electron.ts`, set up from `guardWindowOpens`'s `did-create-window`) keeps each popup's window title as "host — page title": the host comes from the committed address (`getURL()`, refreshed on `did-navigate` and `did-navigate-in-page`), never from the address asked for, so a page that hasn't loaded yet shows nothing or about:blank; the page's own title is held back from the window (`page-title-updated` prevented) and only placed after the host. Hosts show in punycode (lookalike letters can't pass as another site); other schemes show just the scheme. Checked: the `popups` check (a popup's title starts with 127.0.0.1:8771, and stays that way when the page renames itself "accounts.google.com"). To be checked on David's Windows PC: a sign-in popup's title bar reads e.g. "accounts.google.com — Sign in".
  - **Security audit F2 fixed: no tabs or popups without a click.** Electron has no popup blocker, so any page could open tabs, Lookout, or popup windows from a script, as many as it liked. Now `guardWindowOpens` (`src/engine/electron.ts`) lets a page open something only within 5 seconds of a real press or key in it (mouse, keyboard, touch, or a tap, including inside its frames; Electron's `input-event`), and each press opens one thing, as Chrome's rule does (5 seconds gives a sign-in button time to ask its server first). Popup windows get the same rule, so a popup can't open more on its own either (before, it had none at all). Checked: the `popups` check (a script opening a tab on load opens nothing; a clicked link, Enter on a link, and a sign-in style popup still open; a button opening five tabs opens one; a press more than 5 seconds old no longer counts). To be checked on David's Windows PC: sign-in popups ("Sign in with Google") and links opening new tabs work as before.
  - **Security audit F1 fixed: local pages can't read other local files** (the first security audit, 14 Oct 2026, `docs/SECURITY-PLAN.md`). Electron's `GrantFileProtocolExtraPrivileges` fuse was on, so a local (`file://`) web page, say a saved page or an HTML file from an email, could read any other file on the computer with `fetch` (confirmed with a test page reading a file beside it). The fuse is now off (`forge.config.mts`), so local pages get Chrome's limits. Firn's own UI loaded from `file://` and needed it, so it now loads from `firn://app/index.html` (`serveUi` in `src/main.ts`, which serves only files inside the built UI's folder; anything else is a 404). The UI also moved to its own private, in-memory session (`partition: 'firn-ui'` in `UI_WEB_PREFERENCES`), where `firn:` exists and every permission is refused; web pages stay in the default session, can't reach `firn://` at all, and the engine now uses the default session for downloads, permissions, and the request hook (`src/engine/electron.ts`; it used to find it through the window, which was the UI's). Development mode still loads the UI from Vite. Side effect: a local page can no longer fetch the files next to it (as in Chrome); local PDFs and pages showing their own pictures and styles are unaffected. Checked: the `fileaccess` check (a copy of Electron with the fuse off: a local page can't read a file beside it or elsewhere, by `fetch` or `XMLHttpRequest`; a page can't reach `firn://app`; the UI's session is its own and refuses permissions; `forge.config.mts` keeps the fuse off), and a packaged Linux build by hand (the UI loads from `firn://app` with its bridge and styles; `..` tricks get 404). To be checked on David's Windows PC: the installed build opens and looks as before.

### The last release on Electron: no updates, and a goodbye card

Firn is moving to a native Mac app (Swift/WebKit). The Electron code goes to the archived dwurgy/firn-legacy; dwurgy/firn will carry the Mac app. Windows and Linux are dropped, and nothing carries over. This release does two things and nothing else.

- **Auto-updates are off for good.** No updater code is left, and Firn makes no update checks. Checked by `tests/e2e/updates.cjs` (no updater in the code, no update activity in the log).
- **A goodbye card, once.** `src/farewell.ts` holds `FAREWELL_URL`, the one address both link buttons open. It is `https://firnbrowser.com/mac` (the transition page on the website); change that one line if it moves. `src/ui/Farewell.tsx` is the card: Windows/Linux get "This is the last Firn for Windows." with "Read why" and "Close"; Mac gets "Firn is becoming a Mac app." with "See what's next" and "Later" (picked by `window.firn.platform === 'darwin'`). Calm style: title in Fraunces, body in the system font, ink buttons, no warning colors, no icons. Own classes (`farewell-sheet`, `farewell-footer`) because `whatsnew.cjs` finds What's new by `.whats-new-sheet`.
- **When it shows.** A new setting, `farewellSeen` (default false, validated in `cleanSettings`), is set the moment the card opens. In `onUiReady` (`src/main.ts`) it opens instead of What's new, but only once `onboarded` is true (the floating layer can report ready twice, and a fresh install must see the welcome first); `finishWelcome` opens it right after "Welcome in.". It is also in the Firn menu as "A note from David".
- **The link button** sends only `farewell:open-link` (no address from the UI). The main process ignores it unless the card is open, closes the card, and opens `FAREWELL_URL` in a new tab.
- **Checks.** `tests/e2e/farewell.cjs`: shows once after an update instead of What's new, the right words, quiet on the next start, the menu item reopens it, Esc closes it, the link button opens a new tab, and a fresh install gets the welcome first. Every other check seeds `farewellSeen: true` (run.sh, the `.cjs` files that write their own settings, and the demo recorder's seed). The Mac words can't be checked on Linux.
- **Not done on purpose:** the version bump and the CHANGELOG entry (David asks separately and publishes the release himself).
